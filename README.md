# zakupki-parser-eval

Парсер извещений о закупках по 44-ФЗ из Единой информационной системы
(zakupki.gov.ru) — с проверкой каждого поля по независимому источнику.

Разбор списка — это половина работы. Вторая половина — доказать, что в таблице
лежит то же, что на сайте. Здесь для этого используется карточка извещения:
другая страница с другой вёрсткой, поэтому сдвинутое или перепутанное поле
сразу видно как расхождение.

Только стандартная библиотека Python: ни requests, ни bs4, ни lxml.

## Запуск

```bash
python3 fetch.py 5      # 5 страниц поиска (по 50 извещений) -> raw/
python3 parse.py        # raw/ -> out/notices.json, out/notices.csv
python3 verify.py       # сверка случайной выборки с карточками извещений
```

Сеть нужна только в `fetch.py`. Скачанные страницы лежат в `raw/`, поэтому
разбор и сверка воспроизводятся офлайн и не зависят от того, что сайт
показывает сегодня.

## Что вытаскивается

С пяти страниц поиска — **250 извещений**, двенадцать полей на каждое.
НМЦК в выборке от 1 130 ₽ до 898 981 834 ₽.

| поле | что это | заполнено |
|---|---|---:|
| `reg_number` | реестровый номер извещения | 250 / 250 |
| `law` | закон (44-ФЗ) | 250 / 250 |
| `method` | способ определения поставщика | 250 / 250 |
| `status` | этап закупки | 250 / 250 |
| `subject` | объект закупки | 196 / 250 |
| `customer` | заказчик | 250 / 250 |
| `customer_code` | код организации в ЕИС | 250 / 250 |
| `price_rub` | НМЦК числом | 250 / 250 |
| `published` | дата размещения | 250 / 250 |
| `updated` | дата обновления | 250 / 250 |
| `deadline` | окончание подачи заявок | 196 / 250 |
| `url` | ссылка на карточку | 250 / 250 |

На выходе `out/notices.json` и `out/notices.csv` — CSV с точкой с запятой и BOM,
чтобы Excel открывал его без плясок с кодировкой.

## Сверка с карточками

`verify.py` берёт случайную выборку с фиксированным зерном, качает карточки
извещений и разбирает их **отдельным парсером по другой вёрстке**. Совпадение
двух независимых разборов — это и есть доказательство, что поля не съехали.

Выборка 60 извещений, одно к моменту сверки уже было снято с публикации
(404), сверено 59.

| поле | совпало | разошлось | нет в карточке | точность |
|---|---:|---:|---:|---:|
| объект закупки | 45 | 0 | 14 | 100 % |
| способ определения | 59 | 0 | 0 | 100 % |
| НМЦК | 59 | 0 | 0 | 100 % |
| окончание подачи | 44 | 1 | 14 | 97,8 % |
| дата размещения | 59 | 0 | 0 | 100 % |
| код заказчика | 59 | 0 | 0 | 100 % |

**Всего 326 сверок, совпало 325 — 99,7 %.**

Единственное расхождение разобрано и оказалось не ошибкой разбора. Извещение
`0119200000126015714`: в поиске стоит окончание подачи 25.09.2026, в карточке —
28.09.2026, при том что отметка «Обновлено» в обоих местах одна и та же,
22.09.2026. То есть поисковый индекс ЕИС отстаёт от карточки по продлённому
сроку.

Практический вывод для работы с ЕИС: если срок подачи критичен — а он критичен
всегда, — брать его нужно из карточки, а не из выдачи поиска. Список годится,
чтобы отобрать интересные закупки; последнее слово за карточкой.

## Две ловушки вёрстки ЕИС

Обе стоили реальных полей и обе не видны, пока не начнёшь считать заполненность.

**1. HTML внутри атрибута.** У части извещений в блоке заголовка появляется
подсказка:

```html
<div class="registry-entry__header-top__title"
     data-tooltip='<span class="custom-tooltiptext">Закупка по ч.12 ст.93</span>'>
  44-ФЗ Закупка, осуществляемая в соответствии с частью 12 статьи 93
</div>
```

Обычное `class="...title"[^>]*>` обрывается на угловой скобке **внутри кавычек**
атрибута, и в захват уходит кусок подсказки вместо текста блока. Из-за этого
пропадал номер закона у каждого пятого извещения. Конец открывающего тега
приходится искать с учётом кавычек.

**2. Одно поле под двумя подписями.** У централизованных закупок «Заказчик»
превращается в «Организация, осуществляющая размещение» — та же строка, тот же
`organizationCode`, другая подпись. Привязка к одной подписи теряла заказчика
у 70 извещений из 250.

Общий вывод, который и заложен в код: каждое поле берётся по своему якорю
и по списку допустимых подписей, а не по номеру блока. Вёрстка ЕИС меняется,
и привязка к порядку ломается первой.

## Чего в списке действительно нет

У 54 извещений из 250 нет объекта закупки и срока подачи. Это не пропуск
парсера: все 54 — «Закупка, осуществляемая в соответствии с частью 12 статьи 93
Закона № 44-ФЗ», и в её блоке этих полей нет вообще. Проверено по карточкам:
у всех четырнадцати таких извещений, попавших в выборку сверки, поля нет и там.

Отличать «парсер не нашёл» от «в источнике этого нет» приходится явно, иначе
первое прячется за вторым. Поэтому в сверке отдельная колонка «нет в карточке»,
и точность считается только по тем полям, с которыми есть что сравнивать.

## Файлы

| Файл | Что делает |
|---|---|
| `fetch.py` | качает страницы поиска и карточки извещений в `raw/` |
| `parse.py` | разбирает список в `out/notices.json` и `out/notices.csv` |
| `verify.py` | сверяет случайную выборку с карточками, пишет `out/verification.json` |

## Про сертификаты

zakupki.gov.ru работает на сертификате НУЦ Минцифры, которого нет в доверенных
хранилищах macOS и Python: обычный запрос падает с `CERTIFICATE_VERIFY_FAILED`.
Проверка отключается явно и только для этого источника — данные здесь открытые.
